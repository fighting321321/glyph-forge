# 架构说明

## 当前状态

本文件描述的是 **Phase 0 的初始架构思路**，不是最终设计。

当前原则是：先建立清晰的实验边界，再让目录和模块随着真实需求形成。

## 概念分层

可以暂时把 GlyphForge 拆成以下几层：

### 1. Style

描述整套字体共享的视觉参数，例如：

- 字重；
- 字面率；
- 笔画粗细；
- 转角与端点风格；
- 曲线特征；
- Latin / CJK 的比例关系。

### 2. Primitive

最基础的可复用几何或设计元素。

可能包括：

- 基础笔画；
- 路径；
- 控制点；
- 几何参数。

目前不预设最终 Primitive 一定是什么。

### 3. Component

由 Primitive 组成、可在多个字符中复用的较高层结构，例如：

- 偏旁；
- 部首；
- Latin 字母中的共同结构；
- 特定装饰元素。

Component 必须允许上下文相关调整。

### 4. Glyph

一个具体字符的最终字形定义。

Glyph 可能由以下内容构成：

- Component 引用；
- 结构关系；
- 参数覆盖；
- 字符特定修正；
- 最终轮廓。

### 5. Build Pipeline

负责：

- 解析源定义；
- 生成轮廓；
- 写入字体格式；
- 生成字符映射；
- 构建字体文件；
- 执行验证。

### 6. Validation / Preview

负责检查：

- 字体格式是否有效；
- 字符是否缺失；
- 度量是否合理；
- 生成结果是否可视化；
- 不同版本之间是否出现明显回归。

## 一个可能的数据流

```text
Style Parameters
      ↓
Primitives
      ↓
Components
      ↓
Glyph Definition
      ↓
Context / Optical Adjustment
      ↓
Outline
      ↓
Font Build
      ↓
Validation + Visual Review
```

## 重要架构问题

在写大量代码前，需要优先通过实验回答：

1. 源数据采用什么格式？
   - Python 数据结构？
   - JSON / YAML？
   - UFO？
   - 其他领域格式？

2. 几何表示使用什么层级？
   - 最终 Bézier 轮廓？
   - 参数化笔画？
   - 骨架 + 笔画扩展？
   - 混合方案？

3. Component 如何适应不同上下文？

4. 字符特定修正如何表达？

5. 何时生成最终轮廓？

6. 是否需要保留中间表示，便于以后继续编辑？

7. 哪些工作应该直接交给 FontTools 等成熟工具？

## 当前架构原则

- **可检查**：生成过程中的中间数据应该尽可能可观察。
- **可重现**：相同源定义应得到可重复构建结果。
- **可编辑**：不能为了自动化牺牲人工修正能力。
- **渐进抽象**：真实重复出现后再建立抽象。
- **标准优先**：能接入现有字体生态就不要建立封闭格式。
- **设计与构建分离**：视觉设计数据与工程构建逻辑尽量解耦。

## 当前不确定项

以下问题故意保持开放：

- 主要实现语言；
- 最终源格式；
- 是否使用骨架式表示；
- 是否引入约束求解；
- 是否使用机器学习；
- 是否需要 GUI；
- 最终字体覆盖范围。

这些内容应该通过实验和项目需求逐步决定，并记录到 `DECISIONS.md`。
